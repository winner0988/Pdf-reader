# ADR 0015：掃描頁以 Windows 內建 OCR 在獨立的沙盒行程中辨識，只交給它頁面影像

## 狀態
提議中

（工作卡 #99〔B2-10〕。POC：`crates/pdf_worker/tests/ocr_poc.rs`、`crates/pdf_worker/examples/ocr_probe.rs`；沙盒新增的選項見 `crates/sandbox/tests/sandbox.rs` 的 `win32k_is_only_available_when_asked_for`。）

## 背景
- 規格 §2「OCR 引擎」：整合 Tesseract，為掃描件（沒有文字層的圖片型 PDF）產生可搜尋的文字層；開啟掃描件時自動執行；語言包由使用者在設定中自行選擇安裝。
- 目前掃描頁不能搜尋（MVP-10）、也不能選取與複製（MVP-15）。
- 頁面影像來自不受信任的 PDF。依 ADR 0008，處理它的程式碼要在沙盒中執行；app 不連網（ADR 0009 定案前一律零網路）。
- 本 ADR 比較 Tesseract 與 Windows 內建 OCR（`Windows.Media.Ocr`）。

### POC 的發現
POC 以 MuPDF 把 `benign/mixed-text-zh-en.pdf` 的第一頁渲染成影像，放到新的一頁上，做成沒有文字層的「掃描頁」（MuPDF 讀不到任何文字），再以 200 dpi 渲染這一頁，交給沙盒中的 probe 以 Windows 內建 OCR 辨識。

1. **在 worker 自己的沙盒中（停用 win32k）無法辨識**（`recognition_fails_in_the_workers_own_sandbox`）：
   - `windows` crate 匯入 `ole32.dll`，而 `ole32.dll` 靜態匯入 `user32.dll` 與 `gdi32.dll`；win32k 停用時 `user32.dll` 無法初始化，probe 一啟動就以 `STATUS_DLL_INIT_FAILED`（0xC0000142）結束；
   - 延遲載入 `ole32.dll`、自行 `RoInitialize`、以輪詢取代完成回呼之後可以啟動，也列得出語言；
   - 但從記憶體建立點陣（`SoftwareBitmap::CreateCopyFromBuffer`、`LockBuffer`）回傳 E_INVALIDARG；改從 BMP 解碼可以得到點陣；
   - **辨識本身仍回傳 E_INVALIDARG**：Windows 的影像與 OCR 元件需要 win32k（推測是 DirectX 的系統呼叫）。
2. **只保留 win32k、其他限制與 worker 完全相同時可以辨識**（AppContainer 不授予任何 capability，所以沒有網路；Low 完整性；禁止動態程式碼；單一行程；記憶體上限）：
   - `en-US`：「Privacy-first PDF Reader」；
   - `zh-Hant-TW`：中英兩行都正確。中文字之間會多出空格（「隱 私 優 先 的 P D F 閱 讀 器」），要去掉；
   - 本機每頁（Letter、200 dpi）約 0.1–0.15 秒，包含啟動行程。
3. 可用的辨識語言取決於 Windows：
   - 本機（繁體中文 Windows 11）已有 `en-US` 與 `zh-Hant-TW`，不需要另外安裝；
   - CI 的 runner（英文 Windows Server）只有 `en-US`；以 `Add-WindowsCapability` 加入繁體中文的 OCR，超過 20 分鐘仍未完成。所以 CI 只檢查英文，中文在有繁體中文 OCR 的 Windows 上檢查；沒有時確認引擎清楚回報「沒有這個語言」。
4. Tesseract 沒有做 POC：它的原始碼（Tesseract、Leptonica）與語言資料不在預先核准的下載清單中，需要負責人同意才能下載。

## 選項

| 選項 | 內容 | 代價 |
|---|---|---|
| **A. Windows 內建 OCR，在獨立的 OCR 行程（建議）** | 新的小執行檔 `ocr_worker`，沙盒與 worker 相同但保留 win32k；只接收頁面的灰階像素，回傳文字行與位置 | OCR 行程有 win32k（核心攻擊面較大，見「後果」）；引擎不開源；只有 Windows（ADR 0007 首發平台就是 Windows）；可用的語言取決於使用者的 Windows；與規格寫的 Tesseract 不同 |
| B. Tesseract，在 worker 中 | 以 C／C++ 建置 Tesseract 與 Leptonica，連結進 `pdf_worker`，在完全鎖定的沙盒中辨識 | 新增大型 C／C++ 依賴與建置（CMake）；worker 的攻擊面變大；安裝檔要附語言資料（每種語言數 MB 到數十 MB），或讓使用者匯入並驗證；辨識較慢；需要先下載原始碼做 POC |
| C. Tesseract，在獨立的 OCR 行程 | 同 B，但放在另一個完全鎖定（含停用 win32k）的行程，只接收像素 | 同 B 的建置與體積；多一個行程要管理 |
| D. Windows 內建 OCR，在 worker 中 | 讓 worker 保留 win32k | 所有 PDF 的解析都失去 win32k 的防護，違反 ADR 0008 的最小權限：**不採用** |

## 決定

### 引擎
Windows 內建 OCR（`Windows.Media.Ocr`，選項 A）。辨識介面與實作分開（輸入頁面像素，輸出文字行與位置），之後要換成 Tesseract（選項 C）只換 OCR 行程的實作。

### 在哪裡執行
- 新的執行檔 `ocr_worker`，**不連結 MuPDF**，由主行程以 `sandbox` 啟動：
  - 與 `pdf_worker` 相同的限制：AppContainer（自己的 profile `PdfReader.Ocr`，不授予任何 capability）、Low 完整性、Job（單一行程、記憶體上限、主行程結束即終止）、其他緩解措施；
  - 唯一的差別是保留 win32k（`SandboxConfig::allow_win32k`，worker 永遠不設）；
  - 所有使用中的文件共用一個 OCR 行程，逐頁處理。
- **只給它像素**：
  - 流程：該文件的 worker 渲染頁面（灰階，最多 300 dpi）→ 主行程檢查寬高（每邊最多 10,000 像素，即引擎的上限）與位元組數 → OCR 行程；
  - 不給 PDF、檔案 handle、路徑，也不給任何影像檔格式：直接以像素建立點陣，OCR 行程中沒有影像解碼器。
- **回傳**：文字行、每個字的位置（像素座標）。
  - 主行程驗證（行數、字數、長度上限；比照 MVP-15 移除控制字元與雙向文字控制），換算成頁面座標後交給該文件的 worker。
- 失效處理比照 worker（ADR 0012）：每頁逾時（例如 30 秒）即終止，下一頁重新啟動；崩潰只讓該頁沒有 OCR 結果。

### 何時執行
- 開啟文件後，worker 回報每頁是否有文字層、影像是否涵蓋大部分頁面；兩者都符合的頁面才是「掃描頁」。
- 依規格自動執行：背景、優先度最低（畫面的渲染優先）、目前看得到的頁面先做；狀態列顯示進度，可以停止。
- 設定頁（B2-12）可以關閉自動 OCR；關閉後改為手動（「辨識此文件的文字」）。

### 語言
- 使用 Windows 已安裝的辨識語言（`OcrEngine::AvailableRecognizerLanguages`）。預設依使用者的 Windows 語言（`TryCreateFromUserProfileLanguages`）；繁體中文的辨識器也能辨識英文。
- 設定頁列出可用的語言供選擇，並說明如何在 Windows 設定中新增語言。下載由 Windows 處理；**app 本身不下載任何東西**，也不附帶或匯入語言資料。
- 與規格「語言包在設定中由使用者自行選擇安裝」的差別：安裝在 Windows 設定中進行，不在 app 中。

### 結果放哪裡
- **只在記憶體中**，存在該文件的 worker：搜尋（MVP-10）、選取與複製（MVP-15）把它當成文字層使用，畫面上標示「此頁文字由 OCR 辨識，可能有誤」。
- 中文字之間的空格在主行程去掉（引擎會插入空格）。
- 不寫入磁碟、不進最近開啟的檔案或復原日誌。關閉文件即丟棄，重新開啟時再辨識。
- 把結果寫進 PDF 的隱藏文字層（「另存為可搜尋的 PDF」）需要存檔（ADR 0013、B2-02），另開卡。

### 授權與體積
- 不新增套件：`windows` 已在工作區中（主行程在用），只多幾個功能。
- 安裝檔只多一個小執行檔，不附語言資料。
- 引擎是 Windows 的一部分，不需要列入第三方授權清單。

## 後果
- 換來：
  - 已經證明可行：離線、在沙盒中、中英文都正確，每頁約 0.1 秒；
  - 不用建置與維護 C／C++ 的 OCR 引擎，安裝檔幾乎不變，不用管理語言資料；
  - 語言與辨識品質隨 Windows 更新。
- 付出：
  - **OCR 行程保留 win32k**：攻擊者若能以惡意影像攻破 OCR 引擎，可以嘗試利用 win32k 的核心漏洞逃出沙盒。緩解：它只收到像素（沒有檔案格式要解析）、沒有網路與檔案存取、與 worker 分開；
  - 引擎不開源，無法自行稽核；行為可能隨 Windows 更新改變；
  - 只有 Windows；可用的語言取決於使用者的 Windows，其他語言要使用者自己在 Windows 中新增（由 Windows Update 下載，可能很慢）；
  - 與規格指定的 Tesseract 不同：接受本 ADR 時要一併修改規格 §2；
  - 需要安全審查：新的執行檔與行程、`SandboxConfig::allow_win32k`、主行程與它之間的協定。
- 之後若要改變這個決定：換成 Tesseract（選項 C）只換 `ocr_worker` 的實作與它的沙盒設定（改回停用 win32k），加上語言資料的散布方式；協定與 app 其他部分不變。先要下載 Tesseract 的原始碼做 POC。
