# ADR 0015：掃描頁以 MuPDF 內建的 Tesseract 在該文件自己的 worker 中辨識，沙盒不放寬

## 狀態
提議中

（工作卡 #99〔B2-10〕。POC：`crates/pdf_worker/tests/ocr_poc.rs`，以及 `crates/pdf_worker/examples/` 的三個 probe：`ocr_probe.rs`（Windows 內建 OCR）、`mupdf_tesseract_probe.rs`（MuPDF 內建的 Tesseract）、`tesseract_probe.rs`（另外建置的 Tesseract，建置腳本為 `scripts/ocr-poc/build-tesseract.ps1`）。負責人於 2026-09-30 要求兩個方案都做 POC 再決定，並同意下載 Tesseract 的原始碼與語言資料〔#103 的留言〕。）

## 背景
- 規格 §2「OCR 引擎」：整合 Tesseract，為掃描件（沒有文字層的圖片型 PDF）產生可搜尋的文字層；開啟掃描件時自動執行；語言包由使用者在設定中自行選擇安裝。
- 目前掃描頁不能搜尋（MVP-10），也不能選取與複製（MVP-15）。
- 頁面影像來自不受信任的 PDF。依 ADR 0008，處理它的程式碼要在沙盒中執行；依 ADR 0009，app 不連網。
- ADR 0012：每份文件一個 worker，一份惡意 PDF 攻陷它的 worker 後碰不到其他文件。
- Windows 上的 MuPDF 建置一律包含 Tesseract 與 Leptonica，release 的 worker 已經連結其中一部分，只是從不呼叫（見下方 POC 與 [mupdf-binding.md](../architecture/mupdf-binding.md)）。不論本 ADR 如何決定，這些程式碼都已在 worker 中。
- 本 ADR 比較 Windows 內建 OCR（`Windows.Media.Ocr`）與 Tesseract。

### POC
所有 probe 用同一張「掃描頁」：
- 以 MuPDF 把 `benign/mixed-text-zh-en.pdf` 的第一頁渲染成影像，放到新的一頁上。這一頁沒有文字層，MuPDF 讀不到任何文字；
- 再以 200 dpi 渲染這一頁，交給沙盒中的 probe 辨識。

**Windows 內建 OCR**（`ocr_probe`）：
1. **在 worker 自己的沙盒中（停用 win32k）無法辨識**（`recognition_fails_in_the_workers_own_sandbox`）：
   - `windows` crate 匯入 `ole32.dll`，而它靜態匯入 `user32.dll` 與 `gdi32.dll`；win32k 停用時 `user32.dll` 無法初始化，probe 一啟動就以 `STATUS_DLL_INIT_FAILED` 結束；
   - 延遲載入 `ole32.dll`、自行 `RoInitialize`、以輪詢取代完成回呼後可以啟動，也列得出語言；
   - 從記憶體建立點陣（`CreateCopyFromBuffer`、`LockBuffer`）回傳 E_INVALIDARG；改從 BMP 解碼可以得到點陣；
   - **辨識本身仍回傳 E_INVALIDARG**：Windows 的影像與 OCR 元件需要 win32k。
2. **只保留 win32k、其他限制與 worker 相同時可以辨識**：`en-US` 認出英文行；`zh-Hant-TW` 中英兩行都正確，但中文字之間多出空格（「隱 私 優 先 的 P D F 閱 讀 器」）。
3. 可用的語言取決於 Windows：本機（繁體中文 Windows 11）有 `en-US` 與 `zh-Hant-TW`；CI 的 runner（英文 Windows Server）只有 `en-US`，以 `Add-WindowsCapability` 加入繁中超過 20 分鐘仍未完成。

**Tesseract**，兩份，用同樣的 C API 與同樣的語言資料（tessdata_fast 的 `eng`、`chi_tra`）：
1. **MuPDF 內建的那一份**（`mupdf_tesseract_probe`）：
   - `mupdf-sys` 在 Windows 上建置 MuPDF 的 Visual Studio 方案，`libmupdf.lib` 已含 MuPDF 附帶的 Tesseract 與 Leptonica 1.85：
     - Tesseract 是 Artifex 隨 MuPDF 維護的分支，版本標示為 5.0.0-alpha；只有 LSTM 引擎，不含 GUI；
     - Leptonica 不含任何影像格式程式庫（PNG、JPEG、TIFF 等都關閉）；
   - release 的 `pdf_worker.exe` 已連結其中一部分：依 link map，至少有 Tesseract 223 個原始檔中的 123 個、Leptonica 182 個中的 37 個（與 MuPDF 其他原始檔同名的不計），以及 MuPDF 的 `tessocr`、`output-pdfocr`；
   - MuPDF 自己的 OCR 入口（`fz_new_ocr_device`）只能從檔案讀取語言資料（`fopen`），在沙盒中打不開。所以 probe 直接呼叫 Tesseract 的 C API，以 `TessBaseAPIInit5` 從記憶體載入；
   - MuPDF 把 Leptonica 的記憶體配置接到 MuPDF 的 context（`LEPTONICA_INTERCEPT_ALLOC`），所以呼叫前要像 MuPDF 自己一樣，先以 `fz_set_leptonica_mem` 設定。這是 MuPDF 的內部函式，不在公開標頭中；
   - probe 只連結 MuPDF：**不需要另外建置或下載任何原始碼**。
2. **另外建置的 Tesseract 5.5.3**（`tesseract_probe`，搭配 Leptonica 1.87.0）：
   - 以 CMake 從固定版本的原始碼建置成靜態程式庫（SHA-256 驗證；本機約 1 分鐘）；
   - 只有 LSTM 引擎；不含 curl（網路）、libarchive、任何影像格式程式庫，也不含 ScrollView（GUI）。
3. 兩份的結果相同：
   - probe 只匯入 `kernel32`、`ntdll` 與 C／C++ 執行階段，**沒有 `user32`、`gdi32` 或 `ole32`**；
   - **在 worker 自己的沙盒中（停用 win32k，沒有任何放寬）就能辨識**：語言資料與影像都從 stdin 傳入，沙盒不需要開啟任何檔案；
   - `chi_tra`：中英兩行都正確（「Privacy-first PDF Reader」、「隱私優先的 PDF 閱讀器」）；
   - `eng`：英文行正確，中文行是亂碼，所以語言要選對。

| | Windows 內建 OCR | Tesseract（MuPDF 內建） | Tesseract 5.5.3（另外建置） |
|---|---|---|---|
| 沙盒 | 必須保留 win32k | worker 的沙盒，不放寬 | worker 的沙盒，不放寬 |
| 英文、繁中 | 正確（中文字間有空格） | 正確（`chi_tra` 也認得英文） | 正確（`chi_tra` 也認得英文） |
| 每頁時間（含啟動行程） | 0.11–0.19 秒 | 0.11–0.18 秒 | 0.10–0.18 秒 |
| 行程的記憶體峰值 | 54 MB | 25–30 MB | 23–29 MB |
| 語言 | 使用者的 Windows 有哪些就用哪些 | app 附帶，或使用者匯入 | app 附帶，或使用者匯入 |
| 程式碼 | Windows 的一部分 | 已在 worker 中 | 多兩個 C／C++ 專案，與 worker 中 MuPDF 那一份的符號重複 |
| 安裝檔增加 | 0 | 語言資料：eng 4.1 MB、chi_tra 2.4 MB | 程式庫約數 MB，加上語言資料 |
| 版本 | 隨 Windows | 隨 MuPDF | 自行追蹤 |
| 授權 | Windows 的一部分 | Apache-2.0（Tesseract、語言資料）、BSD-2（Leptonica），與 AGPL-3.0 相容 | 同左 |

## 選項

| 選項 | 內容 | 代價 |
|---|---|---|
| A. Windows 內建 OCR，在獨立的 OCR 行程 | 新的 `ocr_worker`，沙盒與 worker 相同但保留 win32k，只收像素 | OCR 行程有 win32k（核心攻擊面，可能被用來逃出沙盒）；共用一個行程就會看到所有文件的頁面，違背 ADR 0012 的隔離；引擎不開源；語言取決於使用者的 Windows；與規格不同 |
| **B. Tesseract，在該文件自己的 worker 中，使用 MuPDF 內建的那一份（建議）** | 在渲染頁面的同一個行程中，以 Tesseract 的 C API 辨識 | 已在 worker 中、從未執行的程式碼開始處理頁面影像（攻擊面變大，但沙盒不變）；版本隨 MuPDF；依賴 MuPDF 的內部函式 `fz_set_leptonica_mem`；安裝檔多語言資料 |
| C. Tesseract，在獨立的 OCR 行程 | 同 B，但在另一個完全鎖定的行程，只收像素 | 共用行程有 A 的跨文件問題，每份文件一個又沒有比 B 多保護什麼；頁面影像要多一次跨行程傳送 |
| D. Windows 內建 OCR，在 worker 中 | 讓 worker 保留 win32k | 所有 PDF 的解析都失去 win32k 的防護：**不採用** |
| E. 同 B，但連結另外建置的新版 Tesseract | 從官方原始碼建置 Tesseract 與 Leptonica | worker 已有 MuPDF 那一份的同名符號（`TessBaseAPI…`、Leptonica 的 `pix…`），再連結一份就會重複定義或混用兩個版本，除非改 MuPDF 的建置；多兩個 C／C++ 專案要建置與追蹤；安裝檔再大數 MB |

## 決定

### 引擎
**Tesseract**（選項 B），**使用 MuPDF 內建、worker 已經連結的那一份**；只用 LSTM 引擎，與規格一致。

### 在哪裡執行
- 在**該文件自己的 worker** 中（ADR 0012），沙盒**完全不放寬**：頁面在 worker 中渲染後直接辨識，影像不離開 worker；一份惡意 PDF 就算攻破 OCR 引擎，碰得到的也只有它自己的內容。
- 依 ADR 0008，worker 不能開啟檔案：語言資料由主行程讀取，以位元組交給 worker，從記憶體載入（`TessBaseAPIInit5`）。
- Leptonica 的記憶體配置接到 worker 的 MuPDF context（`fz_set_leptonica_mem`），辨識完再解除。MuPDF 以一個全域變數記住它，所以同時只能有一個執行緒使用：worker 一次只辨識一頁。
- worker 回傳每一行的文字與位置（頁面座標）；主行程驗證行數、長度與座標，並比照 MVP-15 移除控制字元與雙向文字控制。
- 上限：每頁的辨識時間（逾時即停止該頁）、影像大小（沿用渲染的上限），並占用 worker 的記憶體上限（POC 的峰值約 30 MB）。

### 建置
- 不需要另外建置：Tesseract 與 Leptonica 隨 `mupdf-sys` 建置 MuPDF 時一起建置，版本由固定的 `mupdf` =0.8.0（MuPDF 1.27.2）決定。
- worker 以 FFI 呼叫 Tesseract 的 C API，以及 MuPDF 的 `fz_set_leptonica_mem`、`fz_clear_leptonica_mem`；這些 `unsafe` 集中在 worker 的一個模組。
- 升級 MuPDF（本來就是安全變更）時，一併確認 Tesseract 的 C API 與這兩個函式沒有改變，OCR 的測試也通過。
- 只有 MuPDF 的那一份不夠用時（例如需要新的模型格式），才考慮選項 E，並另立 ADR。

### 語言
- 安裝檔附帶 `eng` 與 `chi_tra`（tessdata_fast，共 6.5 MB）。
- 其他語言由使用者在設定中**匯入** `.traineddata` 檔（app 不下載任何東西）：
  - 主行程檢查大小上限與檔案格式，再存到 app 的本機資料資料夾；
  - 設定頁列出已安裝的語言，讓使用者選擇。
- 預設依使用者的介面語言：繁體中文用 `chi_tra`（也認得英文），其他用 `eng`。

### 何時執行
- 開啟文件後，worker 回報每頁是否有文字層、影像是否涵蓋大部分頁面；兩者都符合的才是「掃描頁」。
- 依規格自動執行：
  - 在背景、優先度最低（畫面的渲染優先），目前看得到的頁面先做；
  - 狀態列顯示進度，可以停止；
  - 設定頁（B2-12）可以關閉，改為手動（「辨識此文件的文字」）。

### 結果放哪裡
- **只在記憶體中**，存在該文件的 worker：搜尋（MVP-10）、選取與複製（MVP-15）把它當成文字層使用，畫面標示「此頁文字由 OCR 辨識，可能有誤」。
- 不寫入磁碟，不進最近開啟的檔案或復原日誌；關閉文件即丟棄。
- 寫進 PDF 的隱藏文字層（「另存為可搜尋的 PDF」）用 B2-02 的存檔，另開卡。

## 後果
- 換來：
  - 沙盒完全不放寬：OCR 與 PDF 解析同樣在停用 win32k 的 AppContainer 中；
  - 每份文件的隔離不變（ADR 0012）；
  - 與規格一致；引擎與語言資料開源、可稽核、可在其他平台使用；
  - 辨識的語言由 app 決定，不取決於使用者的 Windows；
  - 不需要新的 C／C++ 依賴或建置步驟：程式碼已在 worker 中，安裝檔只多語言資料。
- 付出：
  - 已在 worker 中、從未執行的 Tesseract 與 Leptonica 開始處理頁面影像，攻擊面變大。不過輸入只有 worker 自己渲染的像素，Leptonica 不含任何影像解碼器；
  - Tesseract 的版本隨 MuPDF：Artifex 維護的分支，與官方版本（目前 5.5.3）不同步。弱點要和 MuPDF 一樣人工追蹤（`cargo deny` 看不到 C／C++ 程式碼）；
  - 依賴 MuPDF 未公開的 `fz_set_leptonica_mem`，升級 MuPDF 時要確認；
  - 安裝檔變大 6.5 MB（語言資料）；
  - 需要安全審查：worker 的新 FFI、主行程與 worker 之間的新訊息、語言檔的匯入。
- POC 為了比較加了這些，接受本 ADR 後，實作時一併移除：
  - `SandboxConfig::allow_win32k`（只有 Windows OCR 的 POC 使用）與 Windows OCR 的 POC；
  - 另外建置 Tesseract 的腳本、probe 與 CI 工作。
- 之後若要改變這個決定：辨識的介面（像素進，文字行與位置出）與引擎分開，換成其他引擎只影響 worker 內的一個模組；換成需要 win32k 的引擎則要另立 ADR。
