# ADR 0008：PDF 引擎隔離在 pdf_worker 子行程，前端不直接接觸引擎

## 狀態
已接受

## 背景
規格書 §3 要求 PDF 解析與渲染隔離在低權限行程。PDF 是高風險輸入：MuPDF 是 C 函式庫，惡意構造的 PDF 可能觸發記憶體漏洞。Tauri capability 只能限制 WebView 呼叫哪些系統 API，不能保護不安全的 Rust 程式碼、過寬的檔案範圍、供應鏈或 PDF 引擎本身的漏洞。

## 決定
- 應用程式分成三個信任區：
  1. **WebView（前端）**：只負責顯示與互動，不持有任何檔案路徑，也不能直接呼叫 MuPDF。
  2. **主行程（Tauri／Rust）**：擁有使用者授權的檔案存取、設定與 SQLite；是唯一的協調者。
  3. **`pdf_worker`（獨立子行程）**：唯一連結 MuPDF 的程式；以最低權限執行，沒有網路，也不能自行開啟任意路徑。
- 前端只拿得到不透明的文件代號（document handle），不拿得到路徑；檔案一律由主行程透過原生對話框、拖放或命令列參數取得。
- 主行程把「已開啟的唯讀檔案」交給 worker（例如繼承的唯讀 handle 或串流），而不是傳一個讓 worker 自己去開的路徑字串。
- 主行程與 worker 之間使用有版本號、有長度上限的訊息協定；任何來自 worker 的資料都視為不可信，需要驗證。
- worker 崩潰、逾時或超出記憶體上限時，由主行程終止並回報錯誤，不得拖垮主行程；可重新啟動。
- Windows 上至少使用 Job Object（關閉時一併結束、記憶體上限、禁止產生子行程）；是否採用 restricted token／AppContainer 由 POC 決定（見 MVP-04）。
- IPC 合約（前端 ↔ 主行程 ↔ worker）集中定義在獨立模組，並寫成文件（見 MVP-02）。

## 後果
- 換來：引擎漏洞被利用時，影響被限制在沒有網路、沒有任意檔案存取的子行程內。
- 付出：多一層行程間通訊，頁面影像需要跨行程傳輸，要控制延遲與記憶體複製。
- 付出：行程生命週期、重啟與逾時處理是額外要維護與測試的程式碼；fuzzing 與人工安全審查仍然必要，隔離不是萬靈丹。
