# ADR 0013：編輯在文件自己的 worker 中套用，存檔由主行程交出寫入 handle、完整寫好後才取代原檔

## 狀態
提議中

（工作卡 #90〔B2-01〕。POC：`crates/sandbox/tests/sandbox.rs` 的 `duplicated_write_handles_are_write_only`、`crates/pdf_worker/tests/save_poc.rs`。）

## 背景
- 規格 §4–§6 要求編輯（文字、圖片、頁面、註解、表單）與「每次編輯動作即存」的崩潰復原；到目前為止 app 只讀取 PDF。
- ADR 0008：只有 `pdf_worker` 解析 PDF；worker 在 AppContainer 沙盒中，拿不到路徑，也不能自行開啟檔案。開檔時主行程把**唯讀** handle 複製給 worker。
- ADR 0012：每份文件有自己的 worker。
- 會修改 PDF 的卡片（B2-02～B2-09、B2-13）都需要同一套做法：編輯怎麼表示、在哪裡套用、怎麼復原、怎麼寫回檔案而不讓沙盒拿到更多權限。
- 相關的既有規則：
  - 信任以內容雜湊為準（ADR 0002），存檔後內容改變，信任失效；
  - 文件識別碼要寫進 PDF（ADR 0010，提議中）；
  - 作者設定的權限（MVP-19）。
- POC 的發現：
  - 沙盒中的行程可以透過複製進來的**只能寫入** handle 寫檔，不能讀取，也不能刪除或改名；
  - `mupdf` 繫結可以旋轉頁面、刪除頁面、寫到任何 `Write`，可以增量存檔（已簽章檔案的原位元組保持不變）；
  - 刪除頁面後以**增量存檔**，被刪除頁面的內容**仍在檔案中**，任何人都能從位元組讀到；**完整重寫並清除未使用的物件**才會真正移除；
  - 繫結的 `write_to_with_options` 先把整份輸出寫進記憶體，再複製到 `Write`，所以存檔時 worker 需要約一份輸出大小的額外記憶體。

## 選項

### 1. 編輯的表示

| 選項 | 內容 |
|---|---|
| **A. 型別化的編輯指令（建議）** | `ipc_contract` 定義每一種編輯（例如 `RotatePages`、`DeletePages`、`AddHighlight`），主行程以 `validate` 檢查後轉給 worker |
| B. 前端送 PDF 物件或內容串流 | 前端可以寫入任意 PDF 結構，等於把解析器的攻擊面搬到編輯上；也違背「前端不直接接觸引擎」（ADR 0008） |

### 2. 復原與重做

| 選項 | 內容 |
|---|---|
| **A. 指令清單＋從原檔重新套用（建議）** | worker 保留開檔時的原始位元組與已套用的指令；復原時重新開啟原始位元組、套用前 n−1 個指令。實作簡單、結果確定；大檔案的復原需要重新解析（秒級） |
| B. MuPDF 的 journal（`pdf_undo`／`pdf_redo`） | 快，但 `mupdf` 繫結沒有提供，需要在 worker 中新增 `unsafe` FFI |
| C. 每次編輯後在記憶體中增量存一份快照 | 復原快，但記憶體隨編輯次數成長 |

### 3. 寫出

| 選項 | 內容 |
|---|---|
| **A. 主行程建立暫存檔，把只能寫入的 handle 交給 worker（建議）** | 與開檔的唯讀 handle 相同的模式（`Sandboxed::duplicate_write_only`）；worker 寫完回報，主行程確認後以原子方式取代目的地 |
| B. worker 把整份檔案回傳給主行程 | 受 IPC frame 上限（80 MB）限制，需要分段；主行程要多保存一份 |
| C. 讓 worker 自己開啟目的地 | 沙盒必須有檔案系統權限，違反 ADR 0008 |

### 4. 增量更新與完整重寫

| 選項 | 內容 |
|---|---|
| **A. 預設完整重寫並清除未使用的物件；已簽章的文件才用增量更新（建議）** | 刪除的內容真的消失（隱私優先）；簽章仍可驗證 |
| B. 一律增量更新（Acrobat 的「儲存」） | 快、檔案只增不減；但刪除的頁面、註解、表單值都留在檔案中，與本專案的隱私原則衝突 |

## 決定

### 編輯
- 編輯以**型別化的指令**表示，定義在 `ipc_contract`，每個欄位都有上限（頁碼、數量、文字長度），主行程先 `validate`。前端永遠不送 PDF 物件或內容串流。
- 指令在**該文件自己的 worker** 中，對記憶體裡的文件套用；worker 回報更新後的頁數與頁面尺寸等資訊，前端重新渲染受影響的頁面。
- **復原／重做**：worker 保留原始位元組與指令清單。復原時從原始位元組重新開啟並套用前 n−1 個指令；重做再套用下一個。第一版不做快照，若大檔案太慢再依量測加入。
- **權限**（MVP-19）：比照 Acrobat 依 `/P` 決定能否編輯。頁面管理需要第 4 或第 11 位元，註解需要第 6 位元，填寫表單需要第 6 或第 9 位元，其他修改需要第 4 位元；以擁有者密碼開啟時的例外見 #88。

### 存檔
1. 主行程在**目的地同一個資料夾**建立暫存檔（同一個磁碟區，改名才能是原子的），以 `duplicate_write_only` 把 handle 交給 worker（只能寫入，不能讀取、刪除、改名）。
2. worker 以 `write_to_with_options` 寫入 handle，回報寫入的位元組數。
3. 主行程確認大小，不解析 PDF，只檢查開頭（`%PDF-`）與結尾（`%%EOF`）。然後：
   - 目的地已存在：以 `ReplaceFileW` 取代，保留原檔的屬性與權限；
   - 目的地不存在：在同一個磁碟區改名。

   任何一步失敗就刪除暫存檔，**原檔不變**。
4. 預設**完整重寫**並清除未使用的物件（`garbage`）。**已簽章的文件**以增量更新存檔，並提示「為了保留簽章，刪除的內容仍會留在檔案中」。
5. 以密碼開啟的加密文件：保留原本的加密（MuPDF 的預設）；存檔時設定或移除加密另開卡。
6. 上限：輸出不超過 `MAX_DOCUMENT_BYTES`（512 MB）；存檔請求有自己的逾時（例如 5 分鐘），不套用一般請求的 30 秒。worker 的記憶體上限（2 GiB）要容納原檔、文件結構與一份輸出。

### 崩潰復原（規格 §6）
- 指令清單同時是復原日誌：每個指令套用成功後，主行程把它附加到 app 本機資料資料夾（與 `recent.json` 相同）中該文件的日誌檔。
- 正常存檔、選擇「不儲存」或關閉分頁後刪除日誌。
- 開啟檔案時若有日誌、且原檔的大小與修改時間沒變，提示還原；還原就是重新套用指令。
- 日誌可能含有使用者輸入的文字（附註、表單值），只存在本機資料資料夾，並在隱私說明中列出。

### 與其他 ADR 的關係
- **ADR 0002（信任）**：存檔後內容雜湊改變，原本的信任失效，符合 ADR 0002 的設計。
- **ADR 0010（文件識別碼）**：一般存檔**不寫入**文件識別碼；只有使用者明確要求的動作（例如標記為機敏）才寫入，依 ADR 0010 的決定。
- **ADR 0008**：worker 的權限不增加；它只多拿到一個暫存檔的寫入 handle。

## 後果
- 換來：
  - 所有編輯卡片共用一套 IPC、復原與存檔的做法；
  - 沙盒不需要任何檔案系統權限；
  - 存檔失敗不會損壞原檔；
  - 刪除的內容真的從檔案中移除。
- 付出：
  - 完整重寫比增量更新慢，檔案的位元組變化也較大（對同步軟體不友善）；
  - 大檔案的復原要重新解析；
  - 存檔時 worker 需要一份輸出大小的額外記憶體（繫結的限制）；
  - 新的寫入 handle 與存檔命令是安全審查的重點。
- 之後若要改變這個決定：
  - 改成增量更新只需要換寫出選項，但要重新評估隱私說明；
  - 改用 MuPDF 的 journal 需要在 worker 中加入 `unsafe` FFI，並另寫 ADR。
