# ADR 0033：從 XFDF 匯入註解：在這份文件自己的 worker 中以 quick-xml 解析，不接受 DTD 與自訂的實體；只以 app 自己的做法重建支援的註解，整次匯入是一筆可以復原的編輯

## 背景
- **XFDF**（ISO 19444-1）以 XML 交換註解，不必寄整份文件：
  - 根元素是 `xfdf`（命名空間 `http://ns.adobe.com/xfdf/`）；`<annots>` 底下每個註解一個元素（`highlight`、`text`、`ink`、`freetext`⋯），屬性是頁碼（從 0 起算）、位置與樣式，子元素是文字（`<contents>`，或 XHTML 格式的 `<contents-richtext>`）、筆畫（`<inklist>`）、外觀（`<appearance>`）等；
  - `<f href>` 是原本的檔名，`<ids>` 是原本文件的識別碼，`<fields>` 是表單的資料；
  - 座標是那一頁的 PDF 使用者空間，與註解字典的 `/Rect` 相同，沒有套用頁面的旋轉。
- **匯出已經有了**（B5-09，[xfdf-export.md](../architecture/xfdf-export.md)）：「⋯」→「匯出註解（XFDF）…」。
  - worker 直接讀註解字典的 `/Rect`、`/QuadPoints`、`/InkList`、`/L`，主行程寫出 XML。
  - 十一種註解：螢光筆、底線、刪除線、波浪線、附註、手繪、印章、文字方塊、矩形、橢圓、線；屬性有 `flags`、`name`、`color`、`interior-color`、`opacity`、`width`、`inreplyto` 等。
  - 不寫作者、時間、主旨與 `<ids>`；`<f href>` 只有檔名。
  - 文字方塊的字型一律寫成 `Helvetica`；印章寫 PDF 的 14 種標準印章名稱，圖片印章不匯出。
- **app 的註解**（[annotations.md](../architecture/annotations.md)）：
  - 新增都是型別化的編輯（ADR 0013）：`AddHighlight`（也做底線、刪除線、波浪線）、`AddNote`、`AddInk`、`AddStamp`、`AddShape`（矩形、橢圓、線與箭頭）、`AddTextBox`。
  - 顏色與粗細是固定的選項：螢光筆四種（黃色是 `(1, 0.92, 0)`），畫筆與圖形四種（黑、紅、藍、綠），粗細三種（1、2.5、5 pt）；印章是 8 種標準印章（`StampName`）；附註沒有顏色與圖示可選；文字方塊的文字可以是任何顏色，字級 4 到 288 pt。
  - app 建立的註解沒有作者（`/T`）、時間（`/CreationDate`、`/M`）與唯一名稱（`/NM`），worker 的測試檢查它們不存在。
  - 作者不允許註解（`/P` 第 6 位元）時，新增註解的工具都停用，主行程也拒絕。
- **插入頁面怎麼帶註解**（ADR 0019，[merge.md](../architecture/merge.md)）：
  - worker 在沙盒中把 app 支援的註解讀成純淨的資料，再以 app 自己的建立函式重建，來源的字典一個也不複製；
  - 顏色要剛好是 app 的選項（每個分量差 0.02 以內），不是就略過；粗細取最接近的，都差太多就用中等；
  - 文字方塊的字型由主行程準備：有相同的字型家族就用，沒有就照預設的字型清單試，都排不出來就略過。
- **復原與日誌**（ADR 0013，[crash-recovery.md](../architecture/crash-recovery.md)）：
  - 復原是從原檔重新套用前 n−1 個編輯，worker 重啟時也是重播；
  - 編輯的清單就是崩潰復原的日誌，最多 4 MiB；會讓日誌超過上限的編輯被拒絕（`limitExceeded`），畫面請使用者先存檔。圖片印章的圖片、文字方塊準備好的文字記在日誌裡、編輯的旁邊。文字方塊準備好的模型連同它的字型子集一起記（`recovery.rs` 的 `StoredTextBox`）：每個文字方塊有自己的子集，只含它用到的字；在 JSON 裡是十六進位，大小是原本的兩倍；
  - 插入頁面的來源放不進日誌，是唯一的例外（`lost`）。
- **XML 的風險**：DTD 可以宣告實體，一個實體展開成無數個（「十億笑聲」）；外部實體可以讀檔或連網（XXE）；很深的巢狀可以耗盡遞迴的堆疊；整份建成樹時，大檔案很耗記憶體。
- **XML 在 app 裡**：app 自己的程式還沒有解析過 XML。從檔案建立 PDF 時，EPUB、XPS、SVG 這些以 XML 為基礎的格式，由 MuPDF 以它內建的 XML 解析器在那次轉換專用的 worker 中讀。
- **原則**：XFDF 是新的不受信任的輸入，只在沙盒的 worker 中解析（ADR 0008）；主動內容一律不執行、不帶（AGENTS.md 原則 3）；前端拿不到路徑（原則 4）；不連網（原則 1）。

## 選項

### 1. 在哪裡解析

| 選項 | 換來 | 付出與風險 |
|---|---|---|
| **A. 這份文件自己的 worker（負責人選定，也是工作卡的建議）** | 與插入頁面的 `PrepareSource` 相同的模式：主行程讀檔，位元組交給 worker，不受信任的內容只在沙盒中讀；worker 有每一頁的方塊與旋轉，也知道每一頁已經有幾個註解，座標在同一個地方換算與檢查；不用新的行程 | 惡意的檔案進到開著使用者文件的行程。解析器不含 `unsafe`（見 2），沙盒也在（ADR 0008）。卡住時照現在的做法：一般請求的逾時（30 秒）到了就結束 worker、重新開啟文件、重播編輯，文件不會丟 |
| B. 這次匯入專用的 worker | 惡意的檔案碰不到開著的文件 | 每次匯入多啟動一個 worker；它沒有這份文件，頁面的大小與旋轉要另外傳過去，或先留著檔案的座標、套用時再換算，檢查分在兩個地方 |
| C. 主行程 | 最簡單，沒有新的請求 | 主行程有使用者的全部權限；不受信任的格式只在沙盒中解析（ADR 0008 的精神），**不採用** |

### 2. 用哪個 XML 解析器

| 選項 | 換來 | 付出與風險 |
|---|---|---|
| **A. `quick-xml` 0.42.0（負責人選定）** | 已經在 `Cargo.lock` 中（`plist` 1.10.1 → `tauri-utils` → `tauri`）：用同一個版本、不開任何 feature，就不會多一個 crate。整個 crate 是 `#![forbid(unsafe_code)]`，只依賴 `memchr`。一次讀一個事件（pull parser），不建樹、不遞迴。**不處理 DTD**：`<!DOCTYPE …>` 原樣交出（`Event::DocType`），`&名稱;` 也原樣交出（`Event::GeneralRef`），接不接受由我們決定 | pdf_worker 的新直接依賴：`needs-security-review`、`cargo deny`；之後 tauri 升級時，兩邊的版本可能分開 |
| B. `roxmltree` | 唯讀的樹，程式好寫 | 不在依賴樹中，是新的 crate；整份建成樹；它會讀內部 DTD 的實體宣告並展開，正是我們不要的功能 |
| C. 自己寫 | 沒有新依賴 | XML 的細節（CDATA、註解、處理指令、字元參照、屬性值的正規化、編碼）都要自己做對；錯誤與 fuzz 的負擔全在我們 |
| D. MuPDF 內建的 XML 解析器 | 沒有新依賴，worker 裡已經有（從檔案建立 PDF 讀 XML 格式時用的） | C 程式；Rust 的綁定沒有包裝它，要在 pdf_worker 自己寫 FFI 與 `unsafe`；整份建成樹；DTD 與實體怎麼處理要另外驗證 |

### 3. 顏色與粗細不是 app 的選項時

| 選項 | 換來 | 付出與風險 |
|---|---|---|
| **A. 換成最接近的選項（負責人選定）** | 用現有的型別與建立函式（ADR 0019 的重建）；匯入後可以照常改顏色、移動、刪除；app 自己匯出的註解再匯入時完全相同 | 別的軟體的顏色會變，例如純黃色 `#FFFF00` 變成 app 的黃色；透明度、填色、其他的線端與附註的圖示不帶。匯入完成時說明有幾個換了樣式 |
| B. 只匯入剛好是 app 選項的（ADR 0019 插入頁面的規則） | 與插入頁面一致 | 別的軟體的註解大多會被略過：`#FFFF00` 與 app 的黃色 `(1, 0.92, 0)` 差了 0.08，超過 0.02。匯入幾乎只對 app 自己匯出的檔案有用 |
| C. 照檔案的值（任何顏色、透明度、線寬） | 與來源完全相同 | 註解的型別、畫面上的選色、改顏色的編輯都要能處理「不是選項的顏色」，所有註解功能都受影響，超出這張卡；要支援自訂的顏色時另寫 ADR |

### 4. 作者、時間與主旨（`title`、`creationdate`、`date`、`subject`）

| 選項 | 換來 | 付出與風險 |
|---|---|---|
| **A. 不匯入（負責人選定）** | 與匯出相同，也與 app 自己建立的註解相同（沒有 `/T`、`/CreationDate`、`/M`）；別人的名字與時間不會寫進使用者的文件 | 匯入幾位審閱者的檔案之後，看不出哪一則是誰寫的 |
| B. 匯入，寫進註解 | 看得出是誰、什麼時候寫的 | 把別人的個人資料寫進使用者的文件；app 現在沒有地方顯示作者；日期的格式要另外驗證；要改「app 建立的註解沒有作者」的規則與測試。回覆（B5-08，[#445](https://github.com/winner0988/Pdf-reader/issues/445)）的 ADR 會決定作者名稱怎麼來、怎麼顯示，在那之後再看匯入要不要帶 |

## 決定（負責人選定：四組都是 A）

### 範圍：第一版
- 入口：「⋯」→「匯入註解（XFDF）…」，在「匯出註解（XFDF）…」旁邊；命令面板也有。作者不允許註解時停用，並標示原因。
- 系統的開啟對話框只列 `.xfdf`。
- 解析之後：
  - 有可以匯入的註解，而且 `<f href>` 的檔名與目前的文件不同（不分大小寫）時，先問：「這個 XFDF 是給「a.pdf」的，目前的文件是「b.pdf」，位置可能對不上。仍要匯入嗎？」〔仍要匯入〕〔取消〕。沒有 `<f href>` 時不問；
  - 沒有可以匯入的註解：說明略過了幾個、為什麼，文件不變；
  - 匯入之後，狀態列說明「已匯入 N 個註解」，有略過的、換了樣式的再說明各幾個。`Ctrl+Z` 一次拿掉全部。
- 匯入的註解就是 app 的註解：列在註解清單裡，可以修改、移動、刪除；存檔才寫進檔案。
- 不做（工作卡的「不做」）：FDF；表單的資料（`<fields>` 不讀）；把同一則註解合併回去：一律新增，同一個檔案匯入兩次就有兩份。

### 誰做什麼

| 步驟 | 在哪裡 | 內容 |
|---|---|---|
| 1. 選檔與讀取 | 主行程 | 系統的開啟對話框。在**開啟的** handle 上檢查是一般檔案、不超過 `MAX_XFDF_BYTES`；最多讀上限加一個位元組，多了就拒絕（檔案可能在檢查之後變大）。路徑只在主行程 |
| 2. 解析 | 這份文件的 worker | 新的請求：位元組照下面「XML 的規則」解析；讀出支援的註解，把座標換成頁面座標並檢查，對應顏色與粗細。回傳純淨的資料、略過的數目（依原因）、換了樣式的數目、`<f href>` 的檔名（只取最後一段，清理過）。**不改文件** |
| 3. 檢查與準備 | 主行程 | `validate` 回應：頁碼、數目、文字、每個數字都是有限值。比對檔名。有文字方塊時照插入頁面的做法準備字型，**再以日誌的格式（含字型子集）算一次整次匯入的大小**，放不進就整次拒絕並說明（見下面的「日誌」）。保管這次匯入的資料，給它一個編號；前端只拿到編號、數目、原因的種類與兩個檔名 |
| 4. 套用 | 前端 → 主行程 → worker | 前端以現有的編輯命令送 `importAnnotations { import }`；主行程換成完整的資料交給 worker，worker 以 ADR 0019 的重建函式逐一建立 |

- **資料由主行程保管**：與圖片印章的圖片、文字方塊準備好的文字相同，編輯以編號指向它（與 `AddImageStamp` 的 `image` 相同）。復原、重做與 worker 重啟時重播的是這份資料，不再解析 XML。
- **解析的結果只對當時的文件有效**：座標是依當時的頁面換算的。解析之後、匯入之前文件有了別的編輯（例如在問檔名的時候），主行程拒絕這次匯入，前端請使用者再匯入一次。
- **日誌**：這次匯入的資料記在日誌裡、編輯的旁邊，不用插入頁面的 `lost` 例外，所以當機之後匯入的註解也能還原。大小分兩次算：
  - 解析時，worker 以日誌的格式累計註解的資料，超過 `MAX_XFDF_IMPORT_BYTES` 就停（見「上限」）。沒有文字方塊時，沒有其他編輯就一定放得進 4 MiB 的日誌。
  - 文字方塊的字型子集要等主行程準備好字型才有，解析時算不到。主行程準備好之後，以日誌的格式（含十六進位的子集）算整次匯入的大小：沒有其他編輯也放不進日誌時，整次拒絕，說明是文字方塊太多；只是和其他編輯合起來放不下時，照現在的規則拒絕（`limitExceeded`），請使用者先存檔。

### XML 的規則：不合就整個檔案不匯入，說明原因
- 只接受 UTF-8：開頭可以有 UTF-8 的 BOM；有 UTF-16 的 BOM、XML 宣告的 `encoding` 不是 UTF-8、內容不是合格的 UTF-8，都拒絕。
- **有 `<!DOCTYPE …>` 就拒絕**：任何 DTD，內部的或外部的，不讀也不展開。
- 實體參照只接受 XML 預先定義的五個（`&amp;`、`&lt;`、`&gt;`、`&quot;`、`&apos;`）與字元參照（`&#…;`、`&#x…;`，必須是 XML 1.0 允許的字元）；其他名稱一律拒絕。沒有實體的展開，也就不會讀外部的檔案或網址。
- 必須是合格的 XML：開始與結束的標籤成對（`check_end_names`）、同一個元素的屬性不重複、屬性值有引號、只有一個根元素。
- 根元素是 `xfdf`，命名空間是 `http://ns.adobe.com/xfdf/` 或沒有；不是的話就不是 XFDF。
- 處理指令與 XML 的註解略過；CDATA 當成文字。
- 元素最多 `MAX_XFDF_DEPTH`（32）層：XFDF 的註解本身大約 5 層，多的是 `<contents-richtext>` 的格式。解析以堆疊記層數，不遞迴；解析的模組是 `#![forbid(unsafe_code)]`。
- 註解超過 `MAX_SOURCE_ANNOTATIONS`（10,000，與插入頁面的一份來源相同），或資料量超過 `MAX_XFDF_IMPORT_BYTES`：拒絕，不匯入一半。

### 讀哪些註解

| XFDF | 讀的 | 建立成 |
|---|---|---|
| `highlight`、`underline`、`strikeout`、`squiggly` | `page`、`coords`（每 8 個數字一個四邊形，1 到 `MAX_ANNOTATION_QUADS` 個）、`color` | 螢光筆、底線、刪除線、波浪線（`AddHighlight` 的做法） |
| `text` | `page`、`rect`（位置）、文字 | 附註（`AddNote`），用 app 的圖示 |
| `ink` | `page`、`<inklist>` 的 `<gesture>`（1 到 `MAX_INK_STROKES` 筆，合計最多 `MAX_INK_POINTS` 點）、`color`、`width` | 手繪（`AddInk`） |
| `stamp` | `page`、`rect`、`icon` | app 的 8 種標準印章之一（`AddStamp`），名稱要完全相同 |
| `freetext` | `page`、`rect`、文字、`justification`；`<defaultstyle>` 的字級、顏色與字型家族（沒有時用 `<defaultappearance>` 的字級與顏色） | 文字方塊（`AddTextBox`），字型照「誰做什麼」的步驟 3 |
| `square`、`circle` | `page`、`rect`、`color`、`width` | 矩形、橢圓（`AddShape`） |
| `line` | `page`、`start`、`end`、`head`、`tail`、`color`、`width` | 線（`AddShape`）；有一端是箭頭（`OpenArrow`、`ClosedArrow`）時是箭頭：箭頭在 `end` 那一端照原樣，只在 `start` 那一端時兩端對調 |

- **文字**：讀 `<contents>`；沒有 `<contents>`、只有 `<contents-richtext>` 時，取它的純文字（段落與 `<br/>` 換行，樣式不帶）。照附註與文字方塊現在的規則清理（控制字元、雙向控制字元），附註最多 `MAX_NOTE_TEXT_BYTES`（4,096 位元組），文字方塊最多 `MAX_TEXT_BOX_BYTES`（4,096）。
- **`<defaultstyle>` 與 `<defaultappearance>`** 只當成樣式的提示：前者只認 `font`、`font-family`、`font-size`、`color` 四項，後者只認 `Tf`（字級）與 `rg`、`g`（顏色）；其他的不看。字型家族只是名稱，要符合匯出的名稱規則（見「與其他功能的關係」），不合就當成沒有寫；主行程拿它比對字型的清單。
- **座標**：worker 以那一頁的轉換，把 XFDF 的使用者空間換成 app 的編輯用的頁面座標（與匯出相反）。每個數字都要是有限值；註解要碰得到頁面（ADR 0019 的檢查）；還要通過與自己新增時相同的檢查（例如印章每邊至少 `MIN_ANNOTATION_SIDE_PT`〔8 pt〕、矩形不能是空的、線的兩端不能是同一點）。
- **樣式**（選項 3 的 A）：顏色以 RGB 的距離取最接近的選項；粗細取最接近的（1、2.5、5 pt）；字級在 4 到 288 pt 以外時換成最近的那一端。換了的算在「換了樣式」。
- **不讀、不帶**：作者、時間與主旨（選項 4 的 A）；`name`（app 不寫 `/NM`）；`flags`（匯入的註解與 app 建立的相同）；`opacity`、`interior-color`、附註的 `icon` 與 `color`；`<popup>`；外觀（`<appearance>`、`<imagedata>`，外觀一律由 app 重建）；`<f>` 以外的文件資料（`<ids>`、`<fields>`）。

### 略過並計數（其他的照常匯入）

| 原因 | 例子 |
|---|---|
| 不支援的種類 | `caret`、`polygon`、`polyline`、`fileattachment`（內嵌檔案）、`sound`、`link`、`redact` 等；圖片印章，或不是那 8 種的印章名稱（匯出會寫出 14 種標準印章，其中 6 種 app 不能建立）；有 `hidden` 或 `noview` 的註解（看不見的註解匯入後會變成看得見） |
| 回覆 | 有 `inreplyto` 的（app 還沒有回覆，見「與其他功能的關係」） |
| 頁碼不存在 | `page` 不是數字，或不小於頁數 |
| 位置或格式不正確 | 數字不是有限值、個數不對、不在頁面上、太小；附註沒有文字 |
| 超過上限 | 這一個註解太大（四邊形、筆畫、文字）；這一頁加上原有的超過 `MAX_ANNOTATIONS_PER_PAGE`（2,000）；文字方塊超過 `MAX_SOURCE_TEXT_BOXES`（1,000） |
| 字型 | 文字方塊的文字，任何候選字型都排不出來 |

### 上限

| 項目 | 上限 | 在哪裡檢查 |
|---|---|---|
| XFDF 檔案 | `MAX_XFDF_BYTES`（新的常數，16 MiB） | 主行程（開啟的 handle、讀取時）與 worker |
| 元素的層數 | `MAX_XFDF_DEPTH`（新的常數，32） | worker |
| 註解的數目 | `MAX_SOURCE_ANNOTATIONS`（10,000） | worker 與主行程 |
| 一次匯入的資料 | 解析時 `MAX_XFDF_IMPORT_BYTES`（新的常數，3 MiB，以日誌的格式計算，POC 量過再訂）；準備好文字方塊之後，含字型子集的整次匯入要放得進 4 MiB 的日誌 | worker（解析時累計，超過就停）與主行程（準備好之後，以日誌的格式算實際的大小） |
| 每一個註解 | 四邊形 `MAX_ANNOTATION_QUADS`（1,000）；手繪 `MAX_INK_STROKES`（256）筆、`MAX_INK_POINTS`（20,000）點；附註與文字方塊的文字 4,096 位元組；文字方塊的字級 4 到 288 pt；印章每邊至少 8 pt | worker 與主行程 |
| 每一頁 | 原有的加上匯入的不超過 `MAX_ANNOTATIONS_PER_PAGE`（2,000） | worker |
| 文字方塊 | 一次匯入 `MAX_SOURCE_TEXT_BOXES`（1,000），每批準備 `MAX_PREPARE_TEXT_BOXES`（200） | worker 與主行程 |
| 時間 | 解析與套用都在一般請求的逾時（30 秒）內；超過就結束 worker，照現在的做法重新開啟、重播編輯 | 主行程 |
| 一個訊息 | `MAX_FRAME_BYTES`（80 MiB） | 兩端 |

### 命令與請求
- 新的命令（前端 → 主行程）：選擇並解析 XFDF：顯示開啟對話框、讀取、交給 worker 解析，回傳這次匯入的編號與摘要（要匯入幾個、略過幾個與原因、換了樣式幾個、XFDF 的檔名與目前的檔名）。套用用現有的編輯命令送 `importAnnotations { import }`。沒有路徑參數；名稱由實作卡訂，加進 `capabilities/main.json` 與 `src-tauri/allowed-permissions.json`。
- 新的 worker 請求（定義在 `ipc_contract`）：解析 XFDF（位元組），回應是純淨的資料、各種原因的數目與 `<f href>` 的檔名。新的 `WorkerEdit`：匯入（完整的資料）。每個值都有上限，回應先 `validate`。
- 前端拿不到路徑、XML 或註解的資料。

### 與其他功能的關係
- **匯出（B5-09）**：這張卡一起改一件事，其他不變。文字方塊的字型現在一律寫成 `Helvetica`（`<defaultappearance>` 與 `<defaultstyle>` 都是，`src-tauri/src/xfdf.rs`）；改成寫出文字方塊實際的字型家族名稱（只有名稱，不是字型檔），匯出再匯入才會是同一個字型（工作卡的驗收）：
  - **只寫在 `<defaultstyle>` 的 `font-family`**，加上雙引號，例如 `font-family: "Microsoft JhengHei"`。`<defaultappearance>` 照舊寫 `/Helvetica`：`Tf` 的運算元是 `/DR` 裡的資源名稱，不是家族名稱；有空白的家族名稱寫進去，就不是合格的名稱，別的軟體也找不到這個資源。
  - **名稱的規則**：名稱讀自文件裡的文字方塊，文件可能是別人做的，現在只檢查長度（`FontInfo::validate`）。寫出之前檢查：不能有控制字元與看不見的格式字元，也不能有 `"`、`\`、`;`、`<`、`>`、`&`；不合就不寫 `font-family`，照現在寫 `Helvetica`。合規則的名稱放進雙引號，就不必做 CSS 的跳脫；整段 `<defaultstyle>` 仍照 XML 的規則跳脫。
  - 匯入讀 `font-family` 時照同一個規則：不合就當成沒有寫，照預設的字型清單。
- **插入頁面（ADR 0019）**：共用重建的函式與文字方塊的字型準備。ADR 0019 的內容不變：插入頁面仍然只帶顏色剛好是 app 選項的註解。
- **回覆（B5-08，#445）**：回覆的做法由那張卡的 ADR 決定；決定之後，匯入要不要帶回覆（與作者）另開卡。
- **隱私匯出、分享前淨化**：匯入的註解與 app 建立的相同，照現在的規則。
- **機敏文件**：沒有不同；匯入不改文件的機敏標記。

### 測試與 fuzz
- worker（PDF 由 `tests/corpus/generate.py` 產生，XFDF 由測試產生，不放別人的檔案）：
  - 十一種註解匯出，再匯入沒有註解的同一份文件：種類、頁、位置、文字、顏色、粗細與文字方塊的字型都相同；
  - 旋轉的頁、MediaBox 不從 0 開始的頁：位置正確；
  - 惡意的檔案都是拒絕並說明原因，worker 繼續服務、沒有開任何檔案：`<!DOCTYPE>` 與實體的展開（十億笑聲）、外部實體（`SYSTEM "file:///…"`、`"http://…"`）、未宣告的實體、10,000 層的巢狀、超過上限的註解數與資料量、UTF-16、根元素不對、標籤不成對、兩個根元素；
  - 每一種略過的原因各一個；頁碼與座標的邊界（負數、`NaN`、`1e39`、不在頁面上）；
  - 字型家族的名稱：匯出時有空白的名稱加上引號、只在 `<defaultstyle>`，`<defaultappearance>` 仍是 `/Helvetica`；有 `"`、`\`、`;`、`<`、`&` 或控制字元的名稱寫成 `Helvetica`；匯入時不合規則的 `font-family` 用預設的字型清單；
  - 存檔後 `qpdf --check` 通過；匯入的註解沒有 `/T`、`/M`、`/CreationDate`、`/NM`、`/A`、`/AA`，外觀是 app 產生的；整個檔案找不到 `/JS`、`/Launch`。
- 主行程：handle 上的大小檢查與讀取的上限、檔名比對、解析之後文件有了別的編輯、日誌（放得下、放不下、含字型子集之後才放不下時整次拒絕、當機後還原）、復原與重做、作者不允許註解時拒絕。
- 前端：選單、確認的對話框、結果的說明、焦點；無障礙（axe）。
- E2E（工作卡的驗收）：匯出、開另一份相同的文件、匯入，註解相同；惡意的 XFDF 只讓匯入失敗並說明原因，app 照常可以用。
- fuzz：新的目標 `xfdf_import`：輸入是 XFDF，對 `tests/corpus/` 的一份 PDF 解析、`validate`、套用、存檔、重新開啟；種子是測試產生的 XFDF。`worker_messages` 加上新的訊息；`edit_document` 加上新的編輯（它涵蓋每一種 `WorkerEdit`）。
- `docs/security/attack-surface.md` 加上新的命令與請求。

### POC（實作前，不通過就不實作）
1. pdf_worker 加上 `quick-xml` 0.42.0（不開 feature）：`cargo tree` 確認沒有多出 crate；上面惡意的檔案都在解析時拒絕，時間與記憶體都在上限內。
2. 以 Acrobat Reader 與其他常見的軟體（例如 Foxit、PDF-XChange），在 `tests/corpus/` 的文件上加註解再匯出 XFDF（不放進 repo）：確認元素、屬性、`<contents-richtext>` 與印章名稱的對應；匯入後位置正確；也看匯出的檔案有沒有 `<!DOCTYPE>`。
3. 10,000 個各種的註解，以及幾百個中文的文字方塊：解析、準備、套用與復原的時間（30 秒以內）與日誌的大小（含字型子集），據此訂 `MAX_XFDF_IMPORT_BYTES`，也看多少個中文的文字方塊就放不進日誌。

## 後果
- 換來：
  - 別人寄回來的 XFDF 可以匯入，一次復原就拿掉；
  - XML 已知的攻擊（實體的展開、外部實體、很深的巢狀）在解析時就被擋下；解析在沙盒裡，不含 `unsafe`；
  - 匯入的註解與 app 自己建立的完全相同：沒有動作、沒有別人的外觀、沒有作者與時間；
  - worker 的權限不變。
- 付出：
  - pdf_worker 的新依賴（`quick-xml`）、新的請求與編輯、日誌的新內容、新的 fuzz 目標：實作的 PR 要 `needs-security-review`；
  - 別的軟體的顏色、透明度、填色、線端與附註的圖示會換成 app 的；
  - 回覆、看不見的註解、app 不能建立的種類與印章都略過；
  - 匯入幾位審閱者的檔案之後，看不出是誰寫的；
  - 文字方塊很多（尤其是中文）的檔案，可能因為日誌放不下而整次不能匯入；
  - 有 `<!DOCTYPE>` 的 XFDF 都不能匯入：POC 2 發現常見的軟體會寫的話，那些軟體匯出的檔案就不能用。那時再決定要不要接受只有名稱、沒有內部子集也沒有 `SYSTEM` 或 `PUBLIC` 的 `<!DOCTYPE xfdf>`（改這份 ADR，仍要 `needs-security-review`）；
  - 同一個檔案匯入兩次就有兩份。
- 擋不到的：註解的文字是別人寫的（例如假的說明），app 只以純文字顯示。
- 不改變：主動內容一律不執行、不帶；只有 worker 連結 MuPDF，worker 不拿路徑；前端拿不到路徑；ADR 0019；匯出不寫個人資料（文字方塊的字型名稱不是個人資料）。
- 規格 §6 沒有寫到 XFDF 的匯出與匯入，要不要補上由負責人決定（這張卡只動 `docs/adr/`）。`docs/user/03-editing.md`（與 `04-export-and-convert.md` 的「匯出註解（XFDF）」互相連結）、`annotations.md`、`xfdf-export.md` 與 `docs/security/fuzzing.md` 由實作的 PR 寫。
- 之後若要改變這個決定，代價是：
  - 帶回覆：等 B5-08 的 ADR，再另開卡；
  - 帶作者與時間（選項 4 的 B）：改「app 建立的註解沒有作者」的規則與測試，並先決定畫面怎麼顯示；
  - 照檔案的顏色（選項 3 的 C）：另寫自訂顏色的 ADR；
  - 換解析器：只動 worker 的解析模組，請求、編輯與日誌的型別不變，仍要 `needs-security-review`。
