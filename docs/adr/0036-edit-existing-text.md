# ADR 0036：編輯頁面上原有的文字：一次改一行，以 fork 的內容過濾移除舊字，新字用原字型、本機同款字型或最接近的本機字型（標示「已替代」）；掃描頁只改編輯的那一處；另有「修正辨識的文字」，只改隱形文字層、畫面不變

## 狀態
已接受

（負責人於 2026-11-27 在 Claude Code 的對話中接受：先看了 POC〔PR [#725](https://github.com/winner0988/Pdf-reader/pull/725)〕、Acrobat 的做法與這份 ADR 的草稿，每一組都選了建議的做法，也同意第 5 組要的 fork 修改〔[#593 的留言一](https://github.com/winner0988/Pdf-reader/issues/593#issuecomment-7204873524)、[留言二](https://github.com/winner0988/Pdf-reader/issues/593#issuecomment-7205364328)〕。工作卡 B6-08 POC，[#593](https://github.com/winner0988/Pdf-reader/issues/593)；負責人 2026-11-24 加上掃描頁的需求〔[#593 的留言](https://github.com/winner0988/Pdf-reader/issues/593#issuecomment-7135098561)〕。來源是 Acrobat Pro 對照清單（`docs/planning/acrobat-pro-parity.md`）E 區「編輯既有的文字」（P0，缺口排名第 7 項）與 I 區「修正辨識錯的字」（P2）；規格 §4、§6。粗體是負責人選定的做法；實作卡另開。）

## 背景
- **PDF 沒有段落**：頁面上的字是內容串流裡一段段定位好的字形，字型多半是只含這一頁用到的字的**子集**。改字常遇到：缺字、同一行的位置、舊字沒拿乾淨、同一區的連結與註解被誤刪、掃描頁的底色。
- **POC 的結果**（PR #725，不合併；`tests/corpus` 197 行，另有 27 行合成樣本）：
  - 找得到原字型的字典 197/197；本機有同款字型 196/197（唯一沒有的是 Type 3）。
  - 原字型直接能寫新字：語料庫 194/197（多半是沒嵌入的 Helvetica，偏高）；合成樣本 16/27（59.3%），較接近真實文件。其餘要嵌入新的子集（ADR 0018 的做法，每行約多 10–14 KB；舊子集沒人用時隨整份重寫消失）。
  - 能改而且改完搜得到：語料庫 186 行，明確拒絕 11 行，非預期的失敗 0。
  - **MuPDF 的 `pdf_redact_page` 有兩個副作用**：同一區的連結與註解一律刪除（`pdf-clean.c:1167-1169`，就算不畫黑框、不動圖片）；疊在下面的背景文字（例如浮水印）只要框重疊也刪掉。字框要上下各內縮 15%，才不會誤刪行距緊的上一行。
  - **掃描頁**：MuPDF 改圖片的像素（`Pixels`）一律填純白，檔案從 59 KB 變成 302 KB；worker 自己取外框的紙色（中位數）回填、以原格式重新壓縮，只多 186 B，編輯框外的像素平均誤差 0.003。底色有花紋、格線或照片時會留下痕跡。
  - 不能改的情況都偵測得到：Type 3 字型、自訂編碼又沒有 `ToUnicode`、直書、`3 Tr`／`7 Tr`、已簽章、作者禁止修改（`/P`）、座標退化的頁。
- **Acrobat 的做法**（Adobe 的說明頁，2026-11-27 讀）：段落是可以重排的文字方塊；要改的字型必須裝在電腦上，只內嵌在 PDF 裡的話只能改顏色與大小；缺字型時用可以在偏好設定換的替代字型。掃描頁按「編輯」會先辨識，把**整頁轉成可以編輯的文字**，用相近的字型重寫。另一個工具「修正辨識的文字」只列出它沒把握的字讓你改，掃描的畫面不變。
- **app 現在**：
  - 文字方塊是新加的 FreeText 註解（ADR 0018），不能改頁面上原有的字，字型只來自已安裝的字型（主行程讀登錄檔與字型檔，以位元組交給 worker）。
  - 掃描頁的辨識文字只在 worker 的記憶體裡（ADR 0015，CONTEXT.md「掃描頁與辨識文字」）；「另存為可搜尋的 PDF」把它寫成副本裡的隱形文字層（ADR 0028，Tesseract 的 GlyphLessFont、`3 Tr`），ADR 0028 第 7 條把「修正辨識錯的字」列在不做。
  - 編輯是型別化的指令，在文件自己的 worker 裡套用；復原是從原始位元組重播指令；指令清單同時是崩潰復原的日誌（ADR 0013）。worker 不能自己開路徑（ADR 0008）。

## 選項

### 1. 主架構（負責人 1A-1）

| 選項 | 換來 | 付出與風險 |
|---|---|---|
| **1. 真的換掉舊字：以內容過濾移除舊字，再以字型子集寫新字；掃描頁改圖片的像素（負責人選定）** | 舊字確實不在檔案裡；搜尋、複製與畫面一致；和 Acrobat 的方向相同；沿用 ADR 0018 的子集，不加套件 | 要補 fork 的包裝函式（第 5 組）；不重排段落 |
| 2. 白底方塊蓋住舊字，上面放文字方塊 | 最簡單 | 舊字還在，搜得到也選得到，移開方塊就看得到（和 ADR 0016 遮蔽不只蓋黑框同理）；有底色的頁留下白塊；**不採用** |
| 3. 只改隱形的辨識文字 | 不動畫面 | 畫面還是舊字；這是第 6 組的「修正辨識的文字」，不是「編輯文字」 |

### 2. 第一版的範圍（負責人 1A-2）

| 選項 | 換來 | 付出與風險 |
|---|---|---|
| **A. 一次改一行，不重排段落（負責人選定）** | 工作量小、風險小；POC 已經量過 | 改短留白、改長可能蓋到同一行右邊的字（POC 量到 54 pt 與 174 pt），要提示 |
| B. 第一版就做整段重排（Acrobat 的文字方塊） | 和 Acrobat 相同 | 要從定位好的字形重建段落，工作量大很多 |

### 3. 掃描頁（負責人 1A-3）

| 選項 | 換來 | 付出與風險 |
|---|---|---|
| **A. 只改編輯的那一處：用紙的顏色補底，再寫看得到的新字（負責人選定）** | 其他地方保持原本的掃描畫面；檔案幾乎不變大 | 底色不均勻時留下痕跡；新字的字型和掃描的字不完全一樣 |
| B. 像 Acrobat 整頁轉成文字 | 整頁的字都能改 | 整頁的字都變成字型的樣子，辨識錯的字也一起畫上去 |

### 4. 找不到同款字型時（負責人 1b）

| 選項 | 換來 | 付出與風險 |
|---|---|---|
| **A. 用最接近的本機字型，畫面標示「已替代」與字型名稱（POC 的策略 2，負責人選定）** | 一定改得下去；使用者知道換了字型 | 字寬與樣子和原字不同 |
| B. 拒絕並說明缺哪個字型（策略 3） | 不會悄悄換字型 | 很多文件改不了 |

### 5. 怎麼移除舊字（負責人 1c）

| 選項 | 換來 | 付出與風險 |
|---|---|---|
| **A. 在 fork `winner0988/mupdf-rs` 補 `pdf_filter_page_contents` 與 `pdf_new_sanitize_filter`（含 `pdf_sanitize_filter_options` 的 `text_filter`）的安全包裝，逐字決定留下或移除（負責人選定）** | 只移除要改的字，連結、註解、背景文字都留著 | fork 多一段包裝（含 C 呼叫 Rust 的回呼）要維護 |
| B. 用現有的 `pdf_redact_page` | 不改 fork | 同一區的連結與註解一定被刪（POC C.6）；**不採用** |

### 6. 修正辨識的文字（負責人 1d：要做，排在前面）

| 問題 | 選項 | 換來與付出 |
|---|---|---|
| 修正存在哪裡 | **a. PDF 裡原本的隱形文字層（負責人選定）** | 其他閱讀器搜得到修正後的字；和 Acrobat 相同 |
| | b. app 的資料夾 | 不改 PDF；但換電腦、換閱讀器就沒有，電腦上還多一份文件的內容 |
| | c. PDF 的私有字典（`/PieceInfo`） | 只有這個 app 讀得到，仍要同步隱形文字層 |
| 和「編輯文字」怎麼分 | **兩個命令（負責人選定）**：「編輯文字」會改畫面；「修正辨識的文字」只影響搜尋與複製，畫面不變 | 使用者不會以為改了辨識文字畫面就會變 |
| 能改哪些字 | **任何字（負責人選定）** | Acrobat 只讓你改它標成沒把握的字；app 不標也不限制 |

## 決定

### 編輯文字
- 「編輯文字」工具：點一行字，就地出現編輯器（沿用 B7-08 的就地輸入，#719），**一次改一行，不重排段落**。只做橫書（`wmode` 0）。保留原來的字級、顏色、粗斜體、旋轉與傾斜；位置由這一行原來的起點與方向決定。
- 改完的寬度超出原來那一行、或碰到同一行右邊的字時，編輯器顯示提示；不自動挪動其他的字。
- **舊字以 fork 的內容過濾移除**（第 5 組 A），不用 `pdf_redact_page`：
  - 只移除這一行要改的字；同一區的連結、註解、表單欄位與疊在下面的其他文字都留著。
  - 決定哪些字要移除時，看字的 Unicode、位置與內縮後的字框（POC：上下各 15%）；Form XObject 裡的字也處理。
  - 測試要有負向對照：同一區的連結、註解、背景文字與上下兩行都還在；把過濾改成 `pdf_redact_page` 時測試要失敗。
- 新字以內容串流寫在原來的位置（處理 `/Rotate`、頁面的轉換矩陣與 MediaBox 不從 (0, 0) 開始的頁）。

### 字型（新的字用什麼字型）
依序：
1. **原字型**：沒有缺字，而且 `ToUnicode` 涵蓋所有新的字（POC：只涵蓋部分時寫進去會搜不到），就直接用原來的字型資源。
2. **本機同款字型**：主行程依原字型的名稱與特徵（家族名稱、寬度等級、字重、粗斜體、等寬、襯線，POC A 的評分）在已安裝的字型裡找，讀檔後以位元組交給 worker（同 ADR 0018，worker 不開路徑，畫面拿不到路徑）；worker 嵌入新的子集（Type0／Identity-H，附 `ToUnicode`）。
3. **最接近的本機字型**（第 4 組 A）：依等寬、襯線、粗斜體與中日韓文字選最接近的已安裝字型，編輯器標示「已替代：<字型名稱>」，使用者可以改選別的已安裝字型。連最接近的也沒有（例如沒有任何含這些字的字型）就拒絕並說明。
- ADR 0018 的字型規則都適用：只用 TrueType 輪廓、看 `fsType` 授權、名稱當成文字處理。ADR 0018「找不到原字型時不默默換掉」是文字方塊的規則；編輯原有的文字照這一節，而且一定標示。

### 掃描頁的編輯文字
- 字在圖片裡的頁（掃描頁，或有隱形文字層的掃描檔）：使用者點的是辨識出的那一行（ADR 0015 的辨識文字，或檔案裡的隱形文字層），操作和一般的頁相同。
- **只改編輯的那一處**（第 3 組 A）：
  - 取編輯框外圍的紙色（中位數）填掉舊字的像素；新字的顏色取框內最暗的 5%（POC D 的做法）；
  - 以圖片原來的格式寫回（JPEG 照原來的格式重新壓縮，品質由實作卡量測決定）；第一版只處理 8 位元的 RGB／灰階（JPEG、Flate）與 1 位元的黑白圖片，其他的拒絕並說明；
  - 這一區隱形文字層的字一起移除，再寫看得到的新字（字型照上一節）；
  - 對話框提示：「底色有花紋或線條時，可能留下痕跡。」
- 不把整頁轉成文字（Acrobat 的做法）。

### 修正辨識的文字
- **另一個命令「修正辨識的文字」**，和「編輯文字」分開：畫面不變，只改搜尋與複製用的字。命令與編輯器說明「畫面不會改變」。
- **修正存在 PDF 裡原本的隱形文字層**：
  - 只用在檔案裡已經有隱形文字層（`3 Tr`）的頁，不論是 app 的「另存為可搜尋的 PDF」寫的，還是別的軟體寫的。
  - 只有記憶體裡的辨識文字、檔案裡沒有隱形文字層的掃描頁，命令說明「先另存為可搜尋的 PDF，再打開副本修正」，不另外把修正存在 app 的資料夾。
  - 做法和編輯文字相同，只改這個字：以 fork 的內容過濾移除這個字的隱形字形，再以 ADR 0028 的 GlyphLessFont 在原來的框寫新字（`3 Tr`，寬度以 `Tz` 貼著框）。文件裡已經有 app 寫的 GlyphLessFont 就共用，沒有就加一個。
  - **看得到的字一律不動**：過濾只移除看不見的字。worker 要能分辨 `3 Tr` 與看得到的字、`7 Tr` 的裁切字，測試要有負向對照（同一個框裡看得到的字還在）；分辨不出來的頁不能用這個命令。
- **任何字都能改**；不標示、也不限制「沒把握的字」。
- 這擴充了 ADR 0028 第 7 條沒做的「修正辨識錯的字」；ADR 0028 其他的決定不變。

### 不能改的情況
拒絕並說明原因，頁面不變：Type 3 字型、自訂編碼又沒有 `ToUnicode`、直書、`3 Tr`／`7 Tr` 的字（編輯文字）、已簽章的文件、作者禁止修改（`/P`，ADR 0013 的權限）、座標退化的頁。`4`–`6 Tr`（畫出來又當裁切）的字：實作卡先確認偵測得到；偵測不到就列為已知限制。

### 編輯、復原與存檔
- 兩個命令都是 ADR 0013 的型別化編輯：前端只送頁碼、行或字的代號、新的文字與字型的選擇，不送 PDF 物件；每個欄位有上限，主行程先 `validate`。
- 一次編輯是一筆，可以復原與重做；存檔照 ADR 0013。
- 崩潰復原的日誌放字型的子集，不放整個字型（同 ADR 0018）；掃描頁的編輯只記參數，重播時重算像素。日誌含使用者輸入的文字，照 ADR 0013 只放在本機資料資料夾。

### fork
- 在 `winner0988/mupdf-rs` 加 `pdf_filter_page_contents`、`pdf_new_sanitize_filter` 與 `pdf_sanitize_filter_options`（至少 `text_filter`）的安全包裝。`unsafe` 只在 fork 裡；回呼不能讓 panic 穿過 C；MuPDF 的例外照 fork 現有的做法轉成錯誤。
- 照現有的規則：fork 只由 Claude Code 的工作階段在負責人同意後加 commit，不 force push，不向上游提；`main` 改用新的 commit 是依賴變更，要 `needs-security-review`。

### 順序
1. fork 的包裝函式；
2. 修正辨識的文字（負責人：排在前面）；
3. 編輯文字，一般的頁；
4. 編輯文字，掃描頁。

### 不做
重排段落與整段的文字方塊（之後另開卡）；整頁轉成文字；直書；尋找並取代（#593 的「不做」）；app 另外附字型或從網路取得字型（ADR 0018）；改已簽章的文件。

## 後果
- 換來：
  - 頁面上原有的字可以真的換掉：舊字不在檔案裡，搜尋、複製與畫面一致，其他閱讀器看得到新字。
  - 掃描檔辨識錯的字可以修正，修正跟著檔案走；畫面不變的修正與改畫面的編輯分得清楚。
  - 同一區的連結、註解與背景文字不會被誤刪。
- 付出：
  - fork 多一段包裝函式（含回呼）要維護，MuPDF 升級時要一起檢查。
  - 一次只能改一行；改長時可能蓋到右邊的字，只靠提示。
  - 找不到同款字型時字的樣子會變（一定標示「已替代」）。
  - 掃描頁底色不均勻時會留下痕跡；JPEG 會重新壓縮一次。
  - 沒有隱形文字層的掃描頁，要先另存為可搜尋的 PDF 才能修正。
- 之後若要改變這個決定，代價是：
  - 加上段落重排：建立在同一套移除與寫入上，另寫 ADR 決定段落怎麼認。
  - 換掉 fork 的包裝（例如上游 `mupdf-rs` 補上同樣的函式）：只換移除舊字的那一層，編輯指令與檔案格式不變。
  - 讓沒有隱形文字層的掃描頁也能直接修正：要決定修正寫進哪裡（例如在「另存為可搜尋的 PDF」的對話框裡先修正），另開卡。
